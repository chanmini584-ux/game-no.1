> 상태: **승인 완료 — Phase 1 진행 중** · 작성: 팀장(Opus) · 2026-10-09
> 가제 'ICHOR'는 신들의 피를 뜻함. 정식 제목은 스토리 확정 후 정함.

## 0. 목표 수준: 무엇이 가능하고 무엇이 어려운가

엘든링과 젤다는 수백 명이 4~6년 동안 만든 게임이다. 그래픽 품질의 대부분은 **사람이 만든 3D 에셋의 양과 질**(캐릭터 모델, 텍스처, 모션캡처 애니메이션)에서 나온다.

| AI 팀이 잘하는 것 | 어려운 것 |
|---|---|
| 게임 시스템 코드 전부 (전투, AI, 퀘스트, 세이브) | 엘든링급 실사 캐릭터 모델 |
| 스토리, 퀘스트, 대사, 아이템 설명 | 모션캡처 수준의 캐릭터 애니메이션 |
| 셰이더, 절차적 지형·풀·하늘·물·조명 | 수백 시간 분량의 수작업 레벨 디자인 |
| AI 이미지·3D 모델 생성 도구 활용 | |

**그래서 이렇게 진행한다**
1. **스타일라이즈드 아트 방향을 추천한다** (젤다 BotW/TotK, 원신, 하데스 계열). 셰이더와 절차적 생성, AI 에셋으로도 완성도가 나오는 방향이다. 실사 다크판타지(엘든링 톤)도 시안으로는 함께 보여준다.
2. **수직 슬라이스(Vertical Slice)를 먼저 만든다.** 지역 1개를 상업 데모 품질로 완성한 뒤 지역을 늘린다. 실제 인디 스튜디오가 퍼블리셔나 Steam 데모용으로 쓰는 방식이다.

## 1. 기술 스택 — ✅ 확정: **Godot 4.6**

v0.1에서는 Three.js를 추천했지만, 사용자 요청("내가 작업하지 않는다는 전제로 더 나은 방법이 있는지 확인")에 따라 실측한 결과 **Godot 4.6으로 변경**했다.

| | Godot 4.6 (**확정**) | Three.js (기존 추천) | Unreal Engine 5 |
|---|---|---|---|
| 이 환경에서 AI가 실행·확인 | ✅ 고급 렌더러(Forward+) 동작 실측. 그림자, 전역조명, 볼류메트릭 포그 스크린샷 생성 성공 | ✅ WebGL2 동작 | ❌ 실행 불가 |
| 오픈월드 기능 | 자동 LOD, 오클루전 컬링, 내비메시, 애니메이션 상태머신, 물리 등 **내장** | 대부분 직접 구현 | 최고 수준 |
| 그래픽 상한 | 높음 | 중간 | 최상 |
| Steam 출시 | 네이티브 PC 빌드, MIT 라이선스(로열티 없음) | 래퍼가 필요하고 대형 월드 성능이 불리 | 가능 |

상세 근거: `docs/TECH.md`

## 2. 게임에서 '백엔드'와 '프론트엔드'의 정의

- **백엔드 = 게임 로직 코어.** 렌더링과 분리된 GDScript 로직 시스템이다. 전투, 스탯, 적 AI, 퀘스트, 대화, 세이브, 월드 데이터를 포함하고 단위 테스트로 검증한다.
  - 이 단계에서 화면 확인은 **그레이박스**(회색 상자와 캡슐)로만 한다. 디자인 결재 전이므로 아트 작업은 하지 않는다.
- **프론트엔드 = 보이고 들리는 것 전부.** 지형, 식생, 하늘, 물, 조명, 캐릭터 모델과 애니메이션, VFX, UI/HUD, 사운드, 카메라 연출이다.
- 온라인 서버(멀티플레이, 계정)는 범위 밖이다. 이 게임은 싱글플레이다. 나중에 필요하면 연결된 Supabase로 클라우드 세이브와 리더보드를 추가할 수 있다.

## 3. 게임 컨셉 (시스템 관점, 스토리는 Sonnet 담당)

- **장르**: 오픈월드 3인칭 액션 RPG (소울라이크 전투 + 젤다식 탐험)
- **핵심 루프**: 탐험 → 발견(유적·신전·보스) → 전투 → 성장(신의 축복·장비) → 더 깊은 지역
- **전투**: 스태미나, 락온, 회피(무적 프레임), 패링, 강인도(Poise), 콤보, 차지 공격, 원거리 공격
- **그리스 신화 특화 시스템 (초안)**
  - **신의 축복(Boon)**: 올림포스 신과 계약해 빌드를 다양화한다. 예: 제우스(번개), 아테나(방패·패링), 아르테미스(활), 헤르메스(대시·이동), 하데스(생명흡수·소환)
  - **헤스티아의 화로**: 체크포인트이자 부활 지점 (엘든링의 축복에 해당)
  - **신화 생물 보스**: 미노타우로스, 메두사, 키메라, 히드라 등 (스토리팀과 조율)
  - **탐험 기믹**: 헤르메스의 샌들로 활공. 등반은 난도가 높아 확장 목표로 둔다.

## 4. 팀 구성과 모델 배정

| 모델 | 역할 | 담당 업무 |
|---|---|---|
| **Opus** (팀장) | 설계, 핵심 구현, 리뷰, 보고 | 아키텍처와 인터페이스 설계, 고난도 코드(캐릭터 컨트롤러, 카메라, 전투 판정, 렌더링 파이프라인, 셰이더), 통합, 코드 리뷰, 사용자 보고와 결재 요청 |
| **Sonnet** (시니어) | 창작, 중간 난도 구현 | **스토리 바이블 전체**(세계관, 인물, 메인·서브 퀘스트, 대사, 아이템 설명), Opus가 정한 인터페이스에 맞춘 시스템 구현(인벤토리, 퀘스트 엔진, 적 AI 패턴, UI 컴포넌트), 테스트 작성 |
| **Haiku** (주니어) | 반복, 대량, 정형 작업 | 스토리 문서를 JSON 데이터로 변환, 아이템·몬스터 수치 테이블 입력, 스키마 검증, 코드베이스 탐색, 린트·포맷 수정, 번역(한↔영), 문서와 변경 로그 정리 |

### 토큰 절약 원칙
1. **명세를 먼저 쓴다.** Opus가 타입, 인터페이스, 수용 기준(테스트)을 먼저 정한 뒤 위임한다. 팀원이 읽을 범위가 좁아지고 재작업이 줄어든다.
2. **브리프를 짧게 쓴다.** 서브에이전트는 맨 처음부터 시작하므로 필요한 파일 경로와 규칙만 담은 짧은 지시서를 준다. 전체 대화는 넘기지 않는다.
3. **가장 싼 모델부터 고른다.** Haiku로 되면 Haiku, 안 되면 Sonnet에 맡기고, 판단과 설계만 Opus가 한다.
4. **검증은 테스트로 한다.** 팀원 결과물을 Opus가 전부 정독하지 않고 테스트 통과 여부와 diff 요약으로 검토한다.
5. **docs/를 공유 메모리로 쓴다.** 설계 문서를 기준점으로 삼아 같은 설명을 반복하지 않는다.
6. **독립 작업은 병렬로 돌린다.** 서로 의존하지 않는 작업은 동시에 실행해 대기 시간을 줄인다.
7. **이어받기 체계를 둔다.** 대형 프로젝트라 여러 세션에 걸치므로 매 단계를 git에 커밋하고 `docs/PROGRESS.md`에 진행 상황을 기록한다.

## 6. 1차 목표 범위 (수직 슬라이스)

| 항목 | 목표 |
|---|---|
| 오픈 지역 | 1개 (약 1km² 내외, 테마는 스토리팀이 결정) |

| 무기 타입 | 3종 (검+방패, 창, 활) |
| 퀘스트 | 메인 1장 + 서브 3~5개 |
| 플레이 타임 | 2~4시간 |
| 이후 확장 | 지역 추가 (올림포스, 명계, 바다 등) |
